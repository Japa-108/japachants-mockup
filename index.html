The verdict

Dedicated stack from a Home card. Called "Stotras." Two modes.

Where New Home card "Stotras" card joins the existing Home collection (Shortcuts · Routines · Challenges…). Tapping it pushes a dedicated ChantLibraryViewController — not a segmented tab inside Mantras.
Why not Mantras subtab Mantras is a god-controller JAMantraGroupViewController is 1000+ lines with a binary segment state, server-paginated dicts, one reuse pool. Grafting SQLite-backed chants on is bolt-on, not extension.
Name "Stotras" Not "Chants." Too close to chanting (= japa). "Stotras" puts linguistic distance between the reading library and the counting experience.
Mental-model bridge Crosslink from Mantras A small card at the top of the Mantras list: "Looking for longer stotras? →" points into the dedicated stack. Cheap to build; preserves UX continuity.
Two reading modes 📘 Study · ✦ Chant First open of any stotra shows a bottom-sheet picker. Remembered per-stotra. New-user default: Study (so beginners don't land on raw Sanskrit).
Data Bundled SQLite Sanskrit ships in-app (~30MB); other scripts download on first selection. Offline-first — devotional apps fail if network is required. OTA deltas via CDN.

UX review said

Chants mentally belong near mantras, but the app should protect counter primacy. Search is non-negotiable for 1,162 items. Default to Study mode. Chant mode must be full-bleed — hide the tab bar. Drop a weak Home section (Horoscope?) when adding Stotras.

Mobile eng review said

Don't graft onto JAMantraGroupViewController; build a new stack. Use UITextView (not UILabel) for Devanagari ligatures. RecyclerView with stable IDs. Auto-scroll pauses on audio interruption. Bundle per-script SQLite. Deep-links resolve cleanly via a dedicated stack.

Engineering notes (from the mobile review)

iOS placement

New JAChantLibraryViewController pushed from Home card. Do not touch JAMantraGroupViewController — its binary segment state and server-dict datasource can't carry SQLite chants cleanly.

Android placement

New ChantLibraryActivity (or fragment if nav-component-based) launched from HomeFragment. Parallel chants/ package to mantras/. Leave MantrasParentFragment untouched.

Chant mode rendering

iOS: UITableView + UITextView (not UILabel — TextKit handles long Devanagari ligatures; UILabel's CoreText chokes). Auto-sized cells.
Android: RecyclerView + setHasStableIds(true), single VH type. Avoid NestedScrollView.

Auto-scroll interruption

iOS: AVAudioSession.interruptionNotification. Android: AudioManager.OnAudioFocusChangeListener. Pause on transient loss, resume on gain.

Storage

Bundle per-script SQLite: Sanskrit ships in-app (~30MB). Hindi / Tamil / IAST download on first language switch (~10–30MB each). OTA deltas via CDN. Net binary bump ~25–35MB.

Deep linking

japa108://stotra/:slug resolves through a coordinator → pushes ChantDetailViewController. Clean because the library is its own stack.

Fonts

Noto Sans Devanagari + Noto Sans Tamil (SIL OFL — safe to bundle). iOS ≥ 13 renders Devanagari natively; Android pre-API 26 quality varies — bundle Noto to guarantee it.

Accessibility

accessibilityLanguage = "sa" on Sanskrit labels (iOS) / android:textLocale="sa" — otherwise VoiceOver / TalkBack reads Devanagari as English phonemes. Clamp Dynamic Type in chant mode.

Localization

Translations are data rows in SQLite, not Localizable.strings. 1,162 chants × 4 scripts is content, versioned with the DB — not the app bundle.
